What this is, and what it is not

Scope

You asked to test the whole flow before assembly. So this software's job is to be the complete classroom session, end to end, with the robot faked. Every subsystem you will eventually plug in — motors, mic, speaker, LLM, display — exists from day one as an interface with a working stand-in behind it. You run one command and watch a full class happen.

When a real part arrives, you change one line of config and that part becomes real. Nothing else moves. That is the entire design premise.

In scope now

  • Session lifecycle: class open → attendance → greeting → lesson → Q&A → quiz → wrap-up → close
  • Per-student tracking: attendance, participation, answers, scores, engagement signals
  • Teacher dashboard and a robot-display view, both in the browser
  • Two run modes: debug (raw hardware frames) and user (clean demo)
  • Multi-agent orchestration and an MCP context seam
  • Full org → school → class → student isolation

Explicitly not in scope now

  • ESP32 firmware beyond a protocol stub — the embedded intern owns that against a fixed wire contract
  • Real STT/TTS tuning for classroom noise — interface only, keyboard input stands in
  • Auth, billing, OTA updates, cloud sync

Your four rules, and how each is enforced

Constraints

You gave four non-negotiables. Each one needs a mechanism, not just good intentions, or it erodes by week three.

Your ruleThe mechanismHow it fails loudly
Any AI provider by changing config Every provider implements one LLMProvider protocol and self-registers under a string key. Config names the key. Provider code that imports anything outside providers/ fails an import-boundary test.
One file, one purpose Modules are single-responsibility and small. Each pluggable family lives in its own package; each implementation is one file. A lint rule caps module length and flags files exporting more than one public class.
Polymorphic object creation One generic Registry[T] reused by all eight pluggable families. A single container builds the whole system from config. Any direct constructor call outside the container is caught in review — the container is the only place that knows concrete types.
Nothing hardcoded Layered config with typed schema. Prompts, thresholds, timings, servo angles, pin maps, retry counts all live in YAML. A test scans the source tree for bare numeric and string literals in decision positions and fails the build.
The load-bearing idea

The last rule is the one that usually dies first. A hardcoded timeout gets added “just for now” during a demo panic and never leaves. The literal-scanner test is what keeps it honest — it is worth the hour it costs to write.

Layers

Architecture · dependencies point downward only

Each layer may call the layer below it and may not call the layer above. The orchestrator never imports a concrete provider, backend, or store — it only holds interfaces the container handed it.

ENTRY
run.py
Parses mode and overrides, loads config, asks the container for a system, starts it. Roughly forty lines.

↓

WIRING
Config + Container
The only code that knows concrete class names. Reads config, resolves every registry key, injects dependencies. Swapping a provider happens entirely here.

↓

Concrete implementations, one file each, each self-registering. Adding one is dropping in a file. Deleting one breaks nothing else.

The swap engine

Polymorphism · one pattern, eight families

You asked for polymorphic object creation wherever it fits. Rather than eight bespoke factories, there is one generic registry reused eight times. An implementation announces itself with a decorator; the package auto-imports its own modules at load; the container looks up the key config names and builds it.

The practical effect: to add an Ollama provider, you create providers/ollama.py, decorate the class, and set llm.provider: ollama. You touch no other file — no import list, no if-else chain, no registration table.

Why this matters for your flow test

flow.sequence being a config list means you can reorder or drop stages without code changes. Testing a five-minute demo that skips attendance and storytelling is a config edit, not a branch.

The session flow

State machine · this is the thing you want to watch run

This is the sequence you described. Each state is one file in flow/steps/, listed in flow.sequence. The orchestrator advances on completion, timeout, or teacher command — all three thresholds configurable.

01
Class open
Teacher selects class. Scope is bound: org, school, class. Session row created.
02
Attendance
Roll call by voice or dashboard tap. Present students become the session roster.
03
Greeting
School-branded welcome. Namaste gesture fires; audio and motion sync here first.
04
Lesson
Structured segments from content JSON. Display and speech advance together.
05
Interaction
Open Q&A loop. Question attributed to a student, routed to the tutor agent.
06
Quiz
MCQ or oral. Answers scored per student, not per class.
07
Wrap-up
Recap, participation summary, closing gesture.
08
Close
Session sealed, metrics rolled up, dashboard updated.
INTERRUPT
Safety halt
E-stop, obstacle, cliff, tilt, or over-current. Pre-empts any state, stops motion, holds until cleared. Sensor thresholds from config.
INTERRUPT
Teacher pause
Freeze and resume from the dashboard at any point. The teacher is always able to take the room back.

What gets recorded per student

Every state emits events carrying a student id where one applies. That event stream is the only source the dashboard reads — which means the dashboard is correct by construction rather than by a second code path.

Present / absentAttendanceAttendance rate over time
Questions askedInteractionCuriosity and participation score
Answer + correctness + latencyQuizTopic mastery, per-student trend

Judgement call you should make

Attributing a spoken question to a specific student is the hardest part of per-student tracking, and voice alone will not do it reliably in a noisy classroom. For the harness I will attribute via the teacher dashboard — the teacher taps who is speaking. Camera-based or wearable-tag attribution is a real project, not a detail, and should be its own decision later.

Config system

Nothing hardcoded · four layers, last wins

Values resolve through four layers so you can change anything at any scope without editing another. Every key is validated against a typed schema at startup, so a typo fails immediately with a clear message rather than surfacing as odd behaviour mid-demo.

The kinds of things that live in config, not code

  • AI — provider, model id, temperature, max tokens, timeout, retries, streaming on/off, and every prompt as a named template file
  • Flow — the stage sequence, per-stage timeout, advance policy, question limits, quiz length and pass mark
  • Hardware — servo channel map, min/max angle per joint, movement speed, gesture keyframes, sensor pins, obstacle and cliff and tilt thresholds, serial port and baud
  • Speech — engine, language, voice, speaking rate, wake word, silence timeout
  • Runtime — log level, sink list, event retention, dashboard refresh rate, web host and port
Direct answer to your ask

Switching AI vendor mid-test is python run.py --mode user --set llm.provider=anthropic. Nothing else changes, and the offline provider stays available as the fallback so the robot keeps working when a school's internet drops — which your own government-school requirement demands anyway.

Org separation

Multi-tenancy · enforced at the data layer, not by discipline

You chose full separation from day one, which is right — you are selling to school chains and CSR programmes, and retrofitting tenancy later means rewriting every query you have.

The model is Org → School → Class → Student, with sessions bound to a class. Every table carries org_id. The mechanism that makes this real: a TenantScope object is a required argument on every repository method. There is no way to call the data layer without saying which tenant you are, because the function signature will not let you.

LevelHoldsReal-world example
OrgBilling, branding, content library, feature flagsA school chain, or a CSR programme running 40 schools
SchoolRobots, teachers, timetable, language defaultOne campus
ClassRoster, grade, subject, session historyGrade 6-B
StudentAttendance, answers, scores, engagementOne child's record

A test seeds two orgs with deliberately colliding class and student names, runs a session in each, and asserts that neither org's queries can see the other's rows. That test is what makes the guarantee real.

Agents and the MCP context seam

Multi-process AI · separated by responsibility

You asked for AI agents across multiple processes. The useful split is by responsibility, so each agent has a narrow job, its own prompt, and can run on a different model — the safety check does not need the same model as the tutor, and paying top-tier rates for engagement scoring is waste.

AgentJobRuns
TutorAnswers student questions at grade level, refuses off-syllabus driftOn demand, in Interaction
QuizmasterGenerates questions from lesson content, scores free-text answersOn demand, in Quiz
NarratorStorytelling with display cue and gesture markersOn demand
EngagementWatches the event stream, scores participation per studentBackground, continuous
SafetyContent filter on anything spoken to children, plus hardware limit watchAlways, in the path

Why MCP sits in the middle

Agents do not reach into the database. They ask the context layer, which is exposed as an MCP server offering session state, the student profile, and the curriculum slice. Three reasons this is worth the indirection:

  • Tenant safety — context assembly is the one place scope is applied, so an agent cannot accidentally read another school's data
  • Testability — you can snapshot exactly what an agent saw when it gave a bad answer
  • Reuse — the same server serves your own tooling later without a second integration
Honest caveat

MCP adds a hop you do not strictly need for a flow test. I am including it because you named it and because the tenant-safety argument holds on its own — but if the harness feels heavy when we run it, this is the first thing I would collapse into a plain in-process interface. It is a seam, so collapsing it is cheap.

Hardware layer

HAL · built against your actual BOM

Your spec and your BOM disagree — I am following the BOM

The tech spec describes 7 stepper motors (NEMA 17/23 on A4988 / DRV8825 / TB6600). Your selected-components CSV describes a different machine: servos on a PCA9685 — 2× OT5325M shoulders, 4× MG996R neck and elbows — plus 2× Rhino 60RPM encoder DC motors on BTS7960B for drive, an ESP32-S3 as motor controller, 6× HC-SR04, 4× VL53L0X cliff sensors, MPU6050, limit switches, e-stop and an ACS712 current sensor.

The servo build is the better call — lighter, cheaper, far simpler for gestures, and it matches your 7–8 kg target. But your spec document needs updating, because the embedded intern will otherwise buy stepper drivers you no longer need.

Split of responsibility

The Pi does not drive motors directly. The ESP32-S3 owns real-time motion and safety reflexes; the Pi sends intent and receives telemetry over one serial link. This matters: a Python garbage-collection pause must never become a servo glitch or a missed cliff sensor.

Runs on Pi 4Runs on ESP32-S3
Session flow, AI, speech, web UI, databaseServo PWM via PCA9685, drive motors and encoders
Gesture intent — “namaste”Gesture execution — keyframe interpolation
Threshold policy from configSensor polling, e-stop, cliff and tilt cut-out in hard real time

Two backends, one interface

  • default  simulator — no hardware. Accepts every command, simulates travel time, emits fake sensor readings, and logs the exact bytes it would have sent. This is what you run this week.
  • later  esp32_serial — same interface, real serial link. Because the simulator logs real frames, the firmware can be developed and verified against captured traffic before the robot is assembled.

The wire protocol lives in one file that is the shared contract between Python and firmware. Framing, command set, telemetry format and error codes are defined there once, and the embedded intern codes against it independently.
