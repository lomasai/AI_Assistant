Build Prompts

Each prompt is a complete specification: the files to create, the exact interfaces, the config keys it introduces, the events it publishes, a command that proves it works, and the boundary it must not cross. Written so an agent or an intern can execute one without having read the others.

Standing rules for every prompt
  1. Paste one prompt, let it finish, run the acceptance command. Do not start the next until it passes.
  2. Never edit a file outside the prompt's scope. If you cannot finish without doing so, stop and say why — that is an architecture problem, not a coding one.
  3. No value in code that belongs in config. Defaults live only in schema.py. The literal scanner enforces this.
  4. Comments are sparse and human. Explain why, never what. No docstring on every function, no narration of obvious steps.
  5. Every new implementation registers itself with the family's Registry and is selected by a config string.
  6. Commit after each prompt. Fourteen commits, each a system that runs.

Behaviour that matters

  • Drop-oldest, never block. A slow consumer must not stall capture. Count drops and expose them in stats().
  • Each source gets its own thread and its own monotonic seq.
  • picamera2.py must import cleanly on a laptop — guard the import and raise only when open() is called.
  • zoom.py maps 1.0–2.5 to a centred ScalerCrop rectangle for picamera2, and is a no-op elsewhere.

The vision pipeline
app/pipeline.py · 3 files · needs P2, P3, P4

The only place lomas_vision and lomas_face meet. Both packages stay ignorant of each other; this file does the joining.

Order of operations — implement exactly this

FrameBus
  -> downscale to face.downscale_width
  -> detect at face.detect_fps          NOT at capture fps
  -> tracker.update()
  -> matcher.resolve() for NEW tracks only, cropping from the
     FULL RESOLUTION frame, never the downscaled copy
  -> estimate_pose()
  -> attention.update()
  -> publish

Events published

vision.tracks         every detect cycle: track ids, boxes, names, attention
student.identified    a track resolved to an enrolled student
student.left          a track with an identity died
student.disengaged    from AttentionMonitor

Rules

  • Runs in its own thread with a drop-oldest queue. Vision must never stall the session. If the queue backs up, drop and count it; log in debug mode only.
  • Nothing else in the system may read frames directly. If a component wants pixels, it subscribes to the MJPEG stream in P10.
  • Respect privacy.recognition_enabled: false by publishing tracks with student_id=None and skipping the matcher entirely.

The engagement agent has one hard rule

Every nudge is phrased as a question, never as a correction. It must never use the words distracted, attention, listening or concentrate. “Meera, what do you think happens next?” is an invitation; “Meera, you seem distracted” is a machine reprimanding a child in front of her class, and it is the fastest way to get the robot switched off permanently. Put the phrasings in the prompt templates, per language, so a teacher's feedback is a content edit.

Hard performance rules

  • Face boxes are absolutely positioned HTML over the video element, driven by vision.tracks. Never re-encode a frame in Python to draw an overlay.

  • Body text starts at 32px. If it looks absurdly large on your laptop over VNC, it is probably right on a 7-inch panel at 1.5 m.
  • Animate the face, never the layout. Sliding panels are where the frame rate dies.

Enrolment and teacher control
app/web/ui/teacher · 9 files · needs P4, P10

The surface that decides whether teachers keep using the product. Three screens.

Enrolment

  • Live camera, name and roll number, and a required consent checkbox that writes a consent row.
  • 3–4 second head-turn capture with a progress ring and live quality feedback from FrameFeedback.
  • Shows how many vectors were stored. Never displays or saves a captured image; frames are discarded in the same call that embeds them.
  • Consent is enforced server-side, not just in the UI. A POST without a consent reference is rejected.

Live control

  • Video with named boxes, roster with attention state, pause and resume, skip section.
  • Tap-to-attribute which student is speaking — this is how per-student Q&A tracking actually works, since voice alone will not identify a child in a noisy room.
  • A prominent switch that disables nudging for the session. Teachers trusting they can silence it is what makes them willing to leave it on.
  • Pause must halt speech mid-sentence and freeze the flow within 300 ms. Treat that latency as a hard requirement, not a nicety.

Session report

  • Attendance, coverage, the questions students asked, quiz results per student.
  • No engagement scores. No ranking. Nothing a parent could read as a judgement of their child.

Hardware layer and ESP32 protocol

Built against the selected-components CSV, not the older spec document. The spec describes stepper motors; the BOM describes servos. The BOM is correct.

Create

packages/lomas_hal/
  backend.py            HardwareBackend protocol + BACKENDS registry
  protocol.py           THE SHARED CONTRACT WITH FIRMWARE - framing,
                        command set, telemetry, error codes, checksum
  backends/simulator.py default. accepts everything, simulates travel time,
                        emits plausible sensors, logs the exact bytes
  backends/esp32.py     pyserial against the same protocol

Interfaces

class HardwareBackend(Protocol):
    def connect(self) -> None
    def gesture(self, name: str) -> GestureHandle
    def look_at(self, yaw: float, pitch: float) -> None   # eyes follow the speaker
    def move(self, linear: float, angular: float) -> None
    def read_sensors(self) -> SensorReading
    def halt(self) -> None                    # immediate, always honoured
    def disconnect(self) -> None

Division of responsibility — this is not negotiable

  • The Pi sends intent (“namaste”). The ESP32 does execution (keyframe interpolation).
  • The ESP32 owns sensor polling, e-stop, cliff and tilt cut-out in hard real time. A Python garbage-collection pause must never become a servo glitch or a missed cliff sensor.
  • No servo angle appears in code. All of it in config/hardware/gestures.yaml.

If a prompt cannot be completed inside its boundary

Stop and say so. Needing to edit a file outside scope means the architecture is wrong somewhere, and that is worth five minutes of conversation. Every quiet reach across a boundary is a future breakage, and they are far cheaper to catch at the moment they are proposed than three months later when four people depend on them.
