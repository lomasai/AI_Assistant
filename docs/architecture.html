The isolation contract

Five rules · everything else follows from these

You asked that touching one thing never breaks another, and that every feature be testable on its own. That is not a folder-structure problem, it is a dependency problem. These five rules are what actually deliver it, and each one is enforced by a test rather than by review.

1
Packages never import siblings
A capability package may import lomas_core and third-party libraries. Nothing else of ours. lomas_face cannot import lomas_vision — it receives frames as plain arrays. test_imports.py walks the AST of every package and fails on a lateral edge.
2
Packages never import the app
Dependencies point one way: app → packages → core. This is what makes a package droppable into your next product. Same test.
3
Features talk through events, not calls
Attention scoring publishes student.disengaged. The nudge agent subscribes. Neither knows the other exists. Delete either one and the system still runs. This is the rule that actually buys you independence — direct calls between features are what create the breakage you want to avoid.
4
Every feature can be switched off
Each has enabled: true|false in config, and the system must start and run a full lesson with any combination off. A test boots the app once per feature with that feature disabled.
5
No literal in a decision position
Thresholds, timings, angles, model names, ports, prompts — all from config. A scanner test flags bare numbers and strings in comparisons and defaults outside the schema file.
What this buys, concretely

An intern working on face recognition cannot break the quiz. A change to the wake word cannot affect the dashboard. You can run the entire teaching flow on a laptop with no camera, no microphone and no internet, because every port has a stand-in. And when you build your next robot, you copy four folders and they work.

Package map

Six packages, one application, one direction

app/
The integrator. The only code that knows all six packages exist. Wires them from config, runs the session, serves the web UI. Deliberately thin.

↓ may import ↓

lomas_vision
Frames from any source. Knows nothing about faces.
lomas_face
Detection, tracking, identity, pose, attention. Receives arrays, returns data. Never opens a camera.
lomas_speech
Wake word, speech in, speech out, duplex control.
lomas_llm
Providers, routing, language-keyed prompts.
lomas_store
Tenancy, repositories, schema, migrations.
lomas_hal
Servos, sensors, the ESP32 wire protocol, and a simulator.

↓ all may import ↓

lomas_core
Foundation only. Registry, config loader, event bus, clock, errors, logging. Zero domain knowledge — it would make equal sense in a warehouse robot.

The split that matters most is vision and face being separate. Vision produces frames; face consumes arrays. That is why the same recognition code runs against a live Pi camera, a recorded video, or a folder of test images without knowing the difference — and why classroom CCTV later is a new file in lomas_vision and nothing else.

The three integrator files are container.py, orchestrator.py and pipeline.py. Everything else is either a package that knows nothing about the product, or a step or agent that plugs into the flow. If you understand those three files you understand the system.

Why every UI reads the same stream

The robot face, the projector view, the teacher dashboard and the debug overlay are four subscribers to one event stream. There is no second code path assembling data for the dashboard, so the dashboard cannot disagree with what happened. It also means adding a fifth surface later — a parent app, a principal report — is a subscriber, not a feature.

Config surface

One tree · four layers · schema-validated at boot

Layers resolve last-wins: default.yaml → profiles/<mode>.yaml → site.yaml (per school, gitignored) → environment and --set. A typo fails at startup with the key path, never silently at 11am in a classroom.

runtime:    mode, locale, log_level, sinks
tenancy:    org_id, school_id, class_id, scratch_tenant_for_debug

  # later: - id: cctv_1  kind: rtsp  url: ...  zone: back

             match_threshold, reverify_seconds, max_tracks
attention:  enabled, cone_yaw, cone_pitch, window_seconds, threshold,
             min_duration, cooldown_per_student, max_nudges_per_session
speech:
  wake:      enabled, engine, phrase, sensitivity
  stt:       engine, language, silence_timeout, fallback_engine
  tts:       engine, voice_per_language, rate
  audio:     inputs[] (each with zone), output, half_duplex
llm:        provider, model, fallback_provider, temperature, max_tokens,
             timeout, retries, stream, router.thresholds

             questions_per_lesson, quiz_length, pass_mark
content:    language, grade, subject, vocabulary_level, pack_path

agents:     enabled[], per-agent model and prompt overrides

Two keys deserve attention. sources is a list even though you have one camera — that single decision is what makes classroom CCTV and multi-angle capture additive later rather than a rewrite. And speech.audio.inputs is a list with zone ids for the same reason: per-desk microphones become config entries, not a redesign.

Two hard rules in the schema itself

No table stores an image. Enrolment frames are embedded and discarded in the same function call — there is no column to put them in, so a future intern cannot casually add the behaviour.

Attention detail expires. Per-second scores live only in memory. What reaches events is the session aggregate. This is the difference between a teaching aid and a surveillance record of a child, and it is much easier to build in now than to argue about later.

Adding a feature, end to end

Proof the claim holds

Say you want the robot to notice when a student raises their hand. Here is the complete change:

  1. Add packages/lomas_face/gestures.py with a hand-raise detector. It receives arrays and returns data, like everything else in that package.
  2. It publishes a new event, student.hand_raised, added to contracts.py.
  3. Add its config block with enabled: false as the default.
  4. Whatever should react — the interaction step, the teacher dashboard — subscribes to the new event.

No existing file changes behaviour. The detector is off by default, so every existing test passes untouched. Turn it on in one profile, test it there, promote it when you trust it. If it turns out to be a bad idea, delete the file and one config block and there is nothing left behind.

The same shape applies to a new language (a content folder and a voice entry), a new AI provider (one file), a new camera (one file plus a config entry), or a new screen (a subscriber). That is the whole point of the structure.

Hardware and models

Pi 4 today, Pi 5 later, all through config

JobChoiceConfig key
Face detectionYuNet, in OpenCV, ~5–10 ms, gives five landmarks freeface.detector
Head poseDerived from those landmarks, no second model—
RecognitionArcFace or MobileFaceNet via onnxruntime, 30–80 ms, new tracks onlyface.embedder
Wake wordopenWakeWord, no API key, ~10% of a corespeech.wake.engine
Speech in, onlineGroq Whisper large-v3-turbospeech.stt.engine
Speech in, offlineVosk small model per languagespeech.stt.fallback_engine

ReasoningGroq for speed, escalation through your existing routerllm.provider

Moving to a Pi 5 changes profiles/pi.yaml and nothing else — higher detect_fps, more max_tracks, a bigger Vosk model, possibly local reasoning. The point of putting every number in config is that a hardware upgrade is a config commit.

Budget on the Pi 4 at these settings lands around 3.1–3.5 of 4 cores, with Chromium the largest single consumer at roughly 1.0–1.4. Keep the UI pages lean and add the cooling fans; a throttled Pi presents exactly like a software bug.
